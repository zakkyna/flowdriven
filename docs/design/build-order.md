# FlowDriven build order (V1 build plan)

Status: complete for the V1 build, 2026-11-21.

This file owns the build step ids `B-00` to `B-31` and the task ids `B-NN.Tn`. It turns the design set in `docs/design/` into ordered steps for a test-first build: Codex writes the code one task per call, Claude reviews and commits. Each task names the failing tests to write first by their test case ids, which live in `test-cases/journeys.md`, `test-cases/safety.md` and `test-cases/platform.md`. It follows `prd.md` (section 9, V1 scope and the register of behaviours the owner has not seen, and section 10), `architecture.md` (sections 14 and 15), `threat-model.md` (section 8, the security review gates), `test-plan.md` (the loop, the layers, Harness H and the exit criteria), `runner-api.md` (sections 7 and 14), `data-model.md` (section 5.4, the migration tests) and `contributing-plan.md` (B-31). Each step becomes one short plan in `docs/plans/` when it starts; the plan copies the step's tasks and adds nothing else. A file marked "(new)" is created by the task that carries the mark; a file marked "(extended)" is in the repository today and the task adds to it; an unmarked file is in the repository today or is created by an earlier task.

## Decisions for V1

All are Decided for V1 (revisable), 2026-11-21, and apply to every step below.

1. Translations are approved by the owner's own request (English and Bahasa Indonesia, with easy added languages). They are not an Ask-first item.

The language check is `apps/desktop/src/i18n/i18n.test.ts`, run by `pnpm test`. `tools/checks/` and its allowlist stay unchanged. No words live in `packages/*`: the runner and the contracts carry codes and `Line` values only, and `packages/contracts/src/line-keys.ts` (new) lists the keys the runner emits. Electron main draws notifications from fixed `Line` values with no params and passes the registered language codes to the runner at spawn (`--languages=en,id`); there is no menu bar menu. The renderer builds the "Copy report" Markdown from `runs.export` parts and fills the chat result answer lines. The B-31 docs check is TypeScript: `apps/desktop/src/docs-check.ts` (`checkDocs(root)`) and one Vitest test, `apps/desktop/src/docs.test.ts`.
3. V1 bundles the prototype's Plus Jakarta Sans as one variable font file with its OFL license next to it (owner decision 2026-11-22, plan decision 6). The renderer loads it with `@font-face` from `apps/desktop/src/styles/fonts/`, with the system font stack as fallback; nothing is loaded from the internet (NF-23).
4. The tests of the retiring builder-first screens are not deleted. Those screens are unrouted, and their code and tests keep passing on a frozen island: `packages/contracts/src/v1/` (a read-only copy of contract version 1) and `packages/fixtures/src/v1/` (the version 1 sample and fixture client). The root `@flowdriven/contracts` and `@flowdriven/fixtures` become version 2 only after every importer points at the subpaths `@flowdriven/contracts/v1` and `@flowdriven/fixtures/v1` (decision 32). The retired operations stay in the operation table as 12 retired entries; the real runner keeps each one working until the step it leaves with and then answers it `unavailable` with reason `retired`. Removing the island is a later Ask-first item.
5. Packaging and the runner bundle stay out of V1 (B-30). V1 runs from a checkout.
6. No CI change and no new dependency in V1: every V1 step says "Dependency changes: none".

Standing rules exist only for `local_write`, `run_command` and `change`. A risky kind (send, post, pay, delete, merge) always asks: it can never be under "Does on its own", and `flows.confirm` refuses it there with `not_allowed`, reason `always_asks`. Built in B-04, B-05 and B-13.
10. No first run. Turning a schedule on never starts a run. The "Run it now?" offer that follows Save flow stays. Built in B-12.T6 and B-13.T3.

A start with the permission off is refused with "FlowDriven may not run your AI agents." and a button "Turn on permission" that opens the same "Before you start" dialog as Settings; no run is created. 12. Background. V1 adds no menu-bar icon and no Open at login. It keeps today's macOS behaviour: the app stays alive when its window closes, so schedules keep running until the person quits. There is no `background` setting, no `window.setBackground`, no `tray.ts`, no `login-item.ts` and no `starts.next`. Built in B-23.

## 1. How a step is built

1. **Prototype gate.** Build only what the owner approved in the clickable prototype's Guide. Each step names the journeys that must be approved before it starts and lists the PU items (the register in `prd.md` section 9.1) it builds. A PU item goes into the clickable prototype first, is tried and approved by the owner, and only then is its step built. Nothing on the "Removed from V1" list of that register is built.
2. **The step's plan.** When a step starts, one short plan goes into `docs/plans/` (about one page: the goal, what the owner can try at the end, the tasks with files, tests and gate). One review per plan. No code in plans.
3. **Ask first.** V1 has no Ask-first item (decisions 1 to 41). V2, V3 and B-30 name theirs; approving this plan is the yes for exactly the named change and nothing else (AGENTS.md). Anything a task seems to need beyond its named files stops the task with `Blocked:`.
4. **A task is one Codex call.** One area, at most about five code files plus their tests (a mechanical re-point task is the exception: it changes import specifiers only, in the files its Files line counts), run with `-s workspace-write` set explicitly. For each task: write the failing tests first; run them and see each fail for the reason its case gives ("Fails first because"); a test that passes before the code exists is fixed first; write the smallest code that passes; tidy; run `pnpm format`, then `pnpm check`. No test is weakened, skipped or deleted to pass the gate. Codex never commits.
5. **The red run** (decision 16, `test-plan.md` section 1). The first failing run is saved: its command and, for every failing test, the test's name and failure message go to `.workflow/scratch/<task id>-red.txt` (git-ignored, never committed). The task report shows the same names and messages. The Chair compares each message with the case's "Fails first because" line and sends the task back when a test failed for another reason (for example a typo or an import error). Fixtures and test support (the Harness H parts of B-00 and the fakes), the mechanical re-point tasks (they cite no case) and the Chair steps are exempt; the first two have their own small tests or the green gate as their check.
6. **Handoff.** Tick the task only after the gate passes, and add one line under it: `Done by: <tool/model>, <date>. Evidence: <passing command>; red run: .workflow/scratch/<task id>-red.txt.` After two failures stop and write `Blocked: <short reason>`.
7. **Chair steps and owner steps.** A task marked "(Chair step: no network)", "(Chair step: network)", "(Chair step: GUI)" or "(Chair step: commit)" is the Chair's (the session that does Chair steps): Codex skips it and leaves it unticked. Commits, installs and anything that opens a window are Chair steps. Research steps (B-21.T4 and B-22.T1) are Chair steps with no network: they read only the local help and version output of the installed agents and write a synthetic agent profile with hand-typed values; nothing is recorded from a real agent or account (decision 21). A task marked "(Owner step)" (B-30.T3, B-30.T4) is the owner's own: no agent holds or uses a signing, notarization or release secret, and none creates a tag or a release. The real Codex and Claude Code are run only in Chair walks with the owner watching, on a separate data folder, never inside `pnpm check`.
8. **Old tests** (decision 15). A test whose subject V1 deliberately changes is rewritten in the same task as the new behaviour, with an equally strict assertion that cites the flow spec that now decides it. The task report lists it, and the register "Tests that change" in section 6 names each one. No test is deleted to make room for the new behaviour; the tests of the unrouted builder-first screens stay and keep passing.
9. **Security review.** A task marked "Safety-core change" gets one independent security review before its pull request leaves draft. The reviewer did not build the change and reads it as a diff from a checkout of the default branch. Each finding is fixed or recorded as a known limit, and pinned by a `review-*.test.ts` file. The gates per step come from `threat-model.md` section 8 and are repeated in each step.
10. **Done when** the step's tests pass, `pnpm format` then `pnpm check` pass, the security review (where the step has one) has no open finding, and the owner tried what the step says they can try.
11. **Pinning cases.** A case that pins behaviour that exists today, or a source rule, is a pinning case. It is exempt from the red run: its "Fails first because" line starts "Pinning case:", the task report shows its first green run, and a source rule also shows one planted failing sample (a scratch file that breaks the rule, on which the test fails). Every other test is seen failing first.
12. **The Tests list.** A task's Tests list names every test file that its cases' File lines name. A file is marked "(new)" only in the first task that creates it, and "(extended)" when it is in the repository today and the task adds to it or rewrites it. Every file a task names that is not in the repository and that no earlier task creates is marked "(new)".
13. **Line keys.** A task that emits a new `Line` key adds it to `packages/contracts/src/line-keys.ts`, `apps/desktop/src/i18n/en.ts` and `apps/desktop/src/i18n/id.ts`; these three files are allowed in every such task without being named.
14. **The gate stays green.** `pnpm check` passes after every task. A change that would break code that still depends on version 1 waits for the freeze (decision 32); a task whose subject V1 deliberately changes rewrites the tests that pin the old subject in the same task (item 8).

Test layers: L1 unit, L2 UI, L3 runner integration, L4 check tool, L5 Chair walk (`test-plan.md`). Sample names are Build APK and upload it, Fill timesheet, Weekly supplier report, Email triage and Job review. Test files named in a task are the files the cases name; a file marked "(new)" is created by that task.
