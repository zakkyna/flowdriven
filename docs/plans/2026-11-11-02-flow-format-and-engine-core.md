## Decisions made in this plan

Spec 18.4 leaves these to the builder. Each can change in a later plan.
1. The SDK has its own `FlowManifest` (format 1.1), separate from the contracts' read model (format 1). Reason: the SDK is MIT and standalone. Mapping to the read models is plan 02b.
2. Fields that the 20.4 example omits are optional with defaults: `summary` and `description` `""`, `version` `"0.1.0"`, `license` `"UNLICENSED"`, step `title` (the UI shows the id). Reason: the M1 flow must load unchanged. Publishing rules come in phase 2. All objects are strict: an unknown field is an error.
3. A step needs at least one required check, except an `ask` step (its answer is the check) and a loop container (its nested steps carry the checks). Every check is run by the runner, so independence from the worker holds by construction; the validator adds the warning `judged_only` when all required checks are `judge` (spec 9.3: "judged, not verified"). A light flow's last top-level step must be an `ask`, carry a required `user` check, or (a loop) have a last nested step with a required `user` check.
4. Check fields: `command` {`cmd`, `args`}, `files` {`paths`, `min_count`, `max_count`, `min_bytes`, `max_bytes`}, `schema` {`file`}, `contains` and `not_contains` {`pattern` or `patterns`, `ignore_case`} (literal substrings, never regular expressions, because the text can come from outside), `judge` {`rubric` file}, `probe` {`tool`, `args`}, `user`. Every check also has `required` (default true), `summary` and `of` (an output id; default: the step's only declared output when it declares exactly one, else the step's text). A `command` must be declared (9.3 "a declared CLI", 15.2 item 1): `cmd` and `args` must match an entry of `commands` of a `cli_tool` requirement the step `uses`; a `probe.tool` is `<requirement>.<tool>` and must be in that requirement's `tools`.
5. Expressions: paths with `.` and `[n]`; no function calls. A bare step id is a "step view": the step's outputs hoisted next to `status`, `passed`, `failed`, `skipped` and `outputs` (so `rough.score.value` and `page.passed` work); output ids may not be those words, `items` or `choice`. Inside `where` a name resolves on the list element first, then in the enclosing scope. A missing path is `undefined`; a comparison with `undefined` is false except `==` and `!=`, which treat it as `null`; no type coercion.
6. A template (`${...}`) is expanded in one pass: replaced text is never scanned again (spec 20.7 R1 spirit). `$${` is a literal `${`.
7. Content hash (spec 9.6): lines `path\tsha256(bytes)\n`, sorted by the UTF-8 bytes of the path (not by JavaScript's string order); file bytes are hashed as they are; paths are used as given (no Unicode normalisation). "LF line endings" in 9.6 is read as the line endings of the listing, not a rewrite of file contents, so any implementation that hashes the bytes agrees with this one.
8. Until the tool catalog exists (plan 05), the validator classifies a tool as risky by words in its name: `send`, `reply`, `forward` are send; `post`, `publish` are post; `pay`, `purchase`, `buy` are pay; `delete`, `remove`, `trash` are delete; `merge` is merge. Step `risky` and the flow's `approvals.extra_risky` add names; nothing removes one.
9. R4 (20.7): for a flow with a non-manual trigger, every leaf step before the first `ask` (searched in order, inside loops too; no `ask` means all steps) is refused if it uses a risky tool, a `web` or `desktop` requirement with `mode: act`, or is `do: flow` (the child cannot be seen from here, so it is refused). It runs at save (`registerFlow`) and again at every non-manual run start; install is plan 02b. The test "a provider labelled not enforced" waits for the router (plan 05).
10. Storage is a synchronous `Store` interface on `node:sqlite`. One `approvals` table holds `ask` choices and `result_sign_off` items. The audit log is append-only through SQL triggers. Seen keys are kept 30 days (20.3).
11. An item key enters the seen store only when the item `passed`, in the same transaction that sets the item status. A failed, interrupted, capped or duplicate item is never marked seen. A loop without `key` never uses the seen store.
12. `ask.on_expiry`: `end` (default: the run ends `done`, nothing picked, later steps `skipped`) or `fail` (step and run `failed`). A `result_sign_off` expires after 24 hours and fails the run, as the sample client does.
13. `on_item_fail` defaults to `skip`: the item is `failed`, the loop goes on and still `passed`. `stop` marks the rest `skipped` and blocks the run.
14. Item cap: `min(step.max, flow.limits.max_items)`, where `max_items` defaults to 20 only for flows with a non-manual trigger (20.3). Items over the cap are dropped for this run, not marked seen, and one audit entry `items_capped` records how many. `parallel` is read and validated, and the interpreter runs one item at a time (the limit keeper is plan 04).
15. Limits: an attempt's time limit is `step.limits.max_duration`, else `flow.limits.max_duration`, else 30 minutes (11.3); `max_attempts` likewise reads the step's, else the flow's. `max_attempts` caps all attempts of a step, the re-plan attempt included. `max_runs_per_day` counts non-manual starts per UTC day (default 24 when the flow has a non-manual trigger); a manual start is never counted or refused. A start whose trigger kind the flow does not declare is refused.
16. Retries (13.3): 1 + `retry` attempts, then one re-plan attempt, then the run is `blocked`. Exit `quota` or `auth` blocks the run with no retry; exit `interrupted` leaves the step and run `interrupted`.
17. `do: flow` is accepted and validated, but the engine fails such a step with a clear note until child runs exist (plan 04). `builtin` steps run through an injected registry `builtins`, empty by default.
18. The `schema` check uses a documented subset of JSON Schema, hand-written (about 60 lines), and fails closed on any other keyword. `pattern` is left out: a flow's regular expression run on outside text can backtrack for ever in the one runner process (a worker with a timeout is a later plan). Reason for no dependency: Zod's JSON Schema import is not relied on.
19. The demo builds its flow as an object, so it does not wait for Task 10 (YAML).
20. The engine returns plain rows (`RunRow`, `StepRow`, ...). Names and states match the contract; shaping them into `RunDetail` is plan 02b.
21. A `do: ask` step may not sit inside a loop (validator `ask_in_loop`) until plan 04: a choice per item has no inbox shape yet, and "the later steps" of an expired choice are then always top-level. A `user` check inside a loop is allowed (the demo and the 20.4 example need it): the item waits, and approving it continues the same walk.
22. Only declared outputs are stored; the rest of a worker's reply is dropped. Scopes are built with `Object.fromEntries` over declared ids read with `Object.hasOwn`, never with `Object.assign` or index writes keyed by worker text.

## Review Focus

The five conditions most likely to bite that nothing else would exercise, most likely first. Each is pinned by a named test in the task that owns the code.
1. **Seen keys**: a failed, interrupted, capped or duplicate item must not be marked seen, or the owner never sees it again. Task 8: `does not mark failed or capped items seen`, `drops duplicate keys inside one list and never marks a loop without key seen`, `a user check on a nested step holds the run; approve finishes the item and marks it seen`.
2. **Missing data in a condition** (a skipped step, an absent output, a typo): must read as false, never throw and never take a branch by accident. Task 3: `a missing path is undefined and compares false`; Task 8: `a condition inside a loop sees the item's earlier steps`.
3. **Text that looks like a reference or a prototype key** inside outside content (`${params.secret}`, `__proto__`, `constructor`) must stay text. Task 3: `expands a reference once`, `refuses calls, assignment, ternaries and forbidden names`; Task 7: `a missing declared output fails the attempt; undeclared outputs are dropped`; Task 8: `a value that looks like a reference is not expanded`.
4. **A crash mid-step**: the interrupted step must not run again unless it is `idempotent`, and a flow re-registered after the run started must not change that run. Task 8: `after a crash only an idempotent step resumes`, `a run stays pinned to the flow version it started with`.
5. **Answers to a choice**: a pick outside the options, a second answer, an answer after expiry or after the run failed must all be refused, and expiry must apply on every read. Task 8: `refuses picks outside the options and a second answer`, `expiry applies on every read`.

export function canonicalListing(files: FlowFiles): string {
  const rows = [...files].map(([path, bytes]) => {
    assertSafePath(path); // throws FlowFileError("invalid_path")
    return { key: Buffer.from(path, "utf8"), line: `${path}\t${sha256Hex(bytes)}\n` }; // the bytes as they are
  });
  rows.sort((a, b) => Buffer.compare(a.key, b.key)); // UTF-8 byte order, not UTF-16 code unit order
  return rows.map((row) => row.line).join("");
}

Check runner rules: order is automated (`command`, `files`, `schema`, `contains`, `not_contains`), then `judge` and `probe`, then `user`; the outcomes come back in the same order as the input `checks`. If a required automated check fails, later `judge`, `probe` and `user` checks are not run and return `verdict: "pending"` with summary `not run: an earlier check failed`. `user` returns `pending` (the interpreter turns it into an approval). The value a check reads (`of`): the named output; with no `of`, the only declared output when `declaredOutputs` has exactly one, else the text. `contains` needs every pattern, `not_contains` none; patterns pass through `ctx.bind`; the evidence names the pattern and, for `not_contains`, the offset. `files` binds each path with `ctx.bind`, resolves it with `path.resolve(folder, p)`, rejects a path that leaves the folder, also after `realpath` (an absolute path or a link to outside fails with `outside the project folder`), and applies the glob (`*`, `**`, `?`) and the count and size bounds. `schema` validates the value against the schema text in `ctx.files` (text is parsed as JSON first). `command` calls `ctx.runCommand(cmd, args, { cwd: folder, ... })` and fails with the last 2000 characters of stderr as evidence. `judge` fails when the harness returns an empty `evidence`. `defaultCommandRunner` uses `execFile` (never a shell) with `env` holding only `PATH` and `HOME` from the runner's environment, the time limit and the signal. JSON Schema subset: `type` (string or list of `object array string number integer boolean null`), `properties`, `required`, `additionalProperties` (boolean), `items`, `enum`, `const`, `minimum`, `maximum`, `minLength`, `maxLength`, `minItems`, `maxItems`; `$schema`, `$id`, `title`, `description` are ignored; any other keyword (`pattern` included, Decision 18) gives the problem `unsupported schema keyword <name>`.

Interpreter rules (the tests below pin them; where a choice is open, this is it):
1. **Register and start.** `registerFlow` validates with `files` = the keys of its `files` argument and takes `hash` on trust (the folder loader computes it; plan 02b's `flows.import` uses it). `startRun`: newest registered flow (`not_found` if none). A `trigger.kind` other than `manual` that the manifest's `triggers` do not declare is `not_allowed` (`This flow has no <kind> trigger.`). For a non-manual start, `validateManifest` runs again (R4 at run start) and any error is `not_allowed` with its message; then the day is the UTC date of `now`; cap is `limits.max_runs_per_day`, else 24; if `counter("runs:<flowId>", day) >= cap` append audit `run_dropped` {flowId, day} and throw `not_allowed`; else `increment`. Params are the declared defaults plus `options.params`, type-checked by `ParamDecl.type` (`invalid_input`); a required input that is missing is `invalid_input`. Create the run `queued`, freeze `requirements`, set `checking`, call `readiness` (not ready: `blocked` with its reason), then `running`.
2. **Walk.** Top-level steps in order. A step whose row is `passed` or `skipped` is not repeated. At the end the run is `done` with `endedAt`.
3. **Scope** for expressions: `params`, `inputs`, `trigger`, `steps` = a `stepView` per finished step (a loop's view has `items`; an `ask`'s has `choice`), the same views again under their bare ids (Task 8 adds the loop variable and the item's own steps).
4. **Leaf step.** (a) `when` false: row `skipped`, note `skipped: condition false`. (b) `builtin`: run the registered function, else the step fails `unknown builtin`. `do: flow`: the step fails with note `do: flow is not run by this engine yet` and the run is `blocked`. (c) `worker`, `agent`, `skill`: bind `instructions` with `interpolate`; an unresolved reference fails the step with that message, no retry, run `blocked`. (d) Attempts: at most `min(retry + 2, max_attempts ?? Infinity)` (Decision 15); attempt `retry + 2` is the re-plan attempt: first call `harness.replan` with the failures, and if it returns `undefined` stop. Each attempt records an `Attempt` with `worker` = `harness.name`, sets the step and run `running` (`retrying` between attempts), gives the harness an `AbortSignal` from an `AbortController` aborted by `setTimeout` at the time limit (not `AbortSignal.timeout`, which fake timers do not drive; the timer is cleared when the attempt ends), and the request fields of Task 6. `Attempt.exit` is `ok` only when the step passes with that attempt; a failed check, a missing output or a time-out records `failed`; a harness that rejects with `AbortError` after our abort counts as a time-out; any other rejection fails the attempt with the error's message as `lastFailure` and never escapes the engine. Exit `ok`: each declared output must be present in `outputs` (else the attempt failed with `missing output <id>`); only declared outputs are kept (Decision 22); then `runChecks`. Exit `failed` or a time-out: the attempt failed. Exit `quota` or `auth`: step `failed`, run `blocked` (`The harness has no quota left.` or `The harness needs you to sign in.`), stop. Exit `interrupted`: step and run `interrupted`, stop. A required check `failed`: the attempt failed and `lastFailure` is the evidence. A required check `pending` (a `user` check) and none failed: save the outputs on the row, set step and run `waiting_approval`, create a `result_sign_off` approval (payload the result text cut to 4,000 characters, summary `Approve the result of "<title or id>"`, `itemKey` of the row, expires 24 h), and stop. All required checks passed: step `passed`, outputs saved. (e) Attempts used up: step `failed`, run `blocked` with `Blocked at step "<title or id>": checks still failing after <n> attempts.`
5. **Result sign-off.** `decide` refuses in the order of `answerAsk` (rule 10, Task 8): unknown id `not_found`; kind `ask` `invalid_input`; expired; already decided; run not `waiting_approval`. `approve`: approval `approved`, the step `passed` (its `user` check `passed`), then `walk`. `reject`: approval `rejected`, step and run `failed` with `endedAt`, other pending approvals of the run `expired`.
6. **Expiry sweep** (sign-off part). Each pending `result_sign_off` with `expiresAt <= now`, oldest first: state `expired`, `resolvedAt = expiresAt`, step `failed` with note `The approval expired after 24 hours.` (as the sample client), run `failed` with `endedAt = expiresAt`.

7. **Loop.** `when` false skips it. On first entry set the loop row `running` and build and store the items: resolve `for_each` (not a list: step failed, run `blocked`); each element's key is `resolveValue(key)` as a string, or `#<index>` when the loop has no `key`; a repeated key is `skipped` with `skipped: duplicate key`; a key in the seen store is `skipped` with `skipped: seen in an earlier run`; then keep the first `cap` (Decision 14) and mark the rest `skipped` with `skipped: over the item cap` plus audit `items_capped` {loop, dropped}. 11. **Expiry sweep** (`ask` part). An expired `ask` with `on_expiry: end`: step `passed` with `choice: []` and note `nothing picked: the choice expired`; every later top-level step without a row gets a row `skipped` (`skipped: the run ended at an expired choice`); run `done` with `endedAt = expiresAt`. 12. **Resume.** Allowed for `blocked`, `failed`, `interrupted` (else `not_allowed`).
