# Plan 05d: The Approved Build Plan, a Folder for Each Job, and M1 on Real Data Implementation Plan

> **Execution:** one task per Codex call through the handoff rules in AGENTS.md; Claude reviews each task against its gates. Steps use checkbox syntax for tracking.

**Goal:** The Upwork job-review flow (milestone M1, spec 20.8, without publishing by the owner's choice of 2026-11-18) runs end to end from the app on the owner's Mac with Claude Code as the only harness. It reads real Gmail alerts and at most 3 real job pages per run in the owner's own browser. The owner picks jobs in the Inbox and approves a short build plan for each picked job. The owner's skill `prototype-builder` then builds a Flutter web prototype from that approved plan, in a folder of its own, and a proposal draft passes its checks. The first run is attended, with the owner watching; after that the flow runs on the hourly schedule. Nothing is published and nothing is sent.

**Architecture:** (1) A `user` check may say `own_text: true`. The step then declares one text output, and the Inbox card shows that text itself. When the owner approves it, the runner stores the SHA-256 of the text on the step row. A later step that reads the row takes that text as the owner's own, not as outside text, for as long as the stored hash matches the row's output. Every other read stays outside (fail closed), so a step that runs commands gets them only from text the owner approved. (2) A granted folder may say `per_item: true`. A step inside a loop then works in `<granted folder>/<item key>/`, created at its first call: each job's Flutter project has a folder of its own, its commands run there, and its `files` check reads there. (3) M1 splits the skill's work into steps. The `plan` step (the skill, no commands, no folder) writes the plan, the owner approves it, and the `proto` step (the skill, the job's folder, exact `flutter` and `dart` lines) builds from the approved plan only.

**Tech Stack:** only what is on `tools/checks/allowlist.json`: Node 24 built-ins (`node:fs`, `node:path`, `node:crypto`), Zod 4 through `@flowdriven/contracts` and `@flowdriven/sdk`, `yaml` 2.9.1 through `@flowdriven/sdk`, React 19, Electron 45, Vitest, Biome. No dependency is added.

## Decisions made in this plan

All are the chair's call (owner may override), within what the spec leaves to the builder (spec 18.4), except where the owner decided.

1. **Approved text is opt-in and exact (the O5 answer).** A `user` check may say `own_text: true`. Only such a check marks text as the owner's own, so no present sign-off gives that mark by surprise. Its step must declare exactly one output, of type `text`. The Inbox card shows that output itself, and the summary says what the approval does. The text must be at most 4,000 characters (what the card shows, as `MAX_HELD_CHARS` of plan 05b) and free of hidden characters; otherwise the check fails before the Inbox, and the step retries or blocks as for any failed check. On approve, the runner hashes the row's output again and stores `ownerApproved: {output, hash, approvalId, at}` on the row only when it equals the hash the card was made from. The validator also requires the check to be required (`required: false` never makes a sign-off) and allows one `own_text` check per step. No runner code sets `similarGroup` (Fact 4), so an own-text card is never approved in a batch with others. Why: the owner can only vouch for text they saw in full.
2. **Where the mark counts.** In `takesOutsideText`, a row with a valid mark counts as not outside in the two direct reads only: a sibling in the same loop item, and a top-level step. A read through a loop's items, the loop variable, and an expression that cannot be parsed stay as today: outside if any matching row is outside, approved or not. A reference `steps.<id>` to a step inside a loop reaches nothing in the expression scope (Fact 2), and `takesOutsideText` skips it today (`:52-53`); it now counts as outside, so a later change to the scope cannot open it. The mark is checked at each attempt against the row's output at that moment, so a plan that changed after the approval makes the build step outside again. Its block then says "A step that reads outside text cannot run commands. Run them in a step of their own." (Fact 3), and no child starts. Why: the smallest exception that the O5 answer needs.
3. **Approved text keeps its history.** The plan row keeps `outside: true`; the mark sits next to it. The audit gets `own_text_approved` with the step, the item key and the hash, never the text; `own_text_changed` when the output changed between the card and the approval.
4. **A folder for each job (`per_item`).** A granted folder (`~/...`) with `access: read_write` may say `per_item: true`; the validator refuses it on any other ref, on a read-only grant (an item folder is created), and on a step outside a loop. In a loop, the step's folder is `<granted folder>/<item key>`. The key must match `^[a-z0-9][a-z0-9_-]{0,63}$`, so a keyless loop's `#1`, a slash, `..`, a leading dot and an upper-case letter (APFS ignores case, so `AB` and `ab` would share a folder) are refused with "This step's item has no name that can be a folder (<id>)." The item folder is created with mode 0700 at the first call, and its real path must equal the joined path after the fold of `folders/extra.ts`, so a symlink or a file in its place is refused as moved. ## Known limits

- **The build runs code it writes.** `flutter test` and `flutter build` run Dart code that the build step wrote, and `flutter create`, `flutter pub get` and `flutter build` may fetch Dart packages from the internet, all with the owner's rights and no OS sandbox. - **The build's evidence is weak.** The worker can write in the job's folder, so it could write the two files the `files` checks look for without building. A folder that already holds a build from an earlier run passes them too. The owner looks at the built prototype in Task 9.
- **Item folders are never removed** by FlowDriven; each job's folder stays in `~/job-review/prototypes/`.
- From plan 05c, unchanged: Withdraw takes effect at the next attempt, so a running step keeps its folders until it ends (up to 150 minutes here); closing a laptop's lid sleeps the Mac even during a long step; a `command` check stays "cannot enforce"; commands run with the owner's rights and no OS sandbox; a file that an earlier step wrote is not marked as outside text; a hung call waits until its limit; an approval inside a long step re-runs the step from its start; a pick releases a named tool for the whole step; the attended first run is a procedure, not a rule; the refused programs are a list, and the risky-word rules match any word (R2-F3, by the owner's choice); the flow hash has no LF normalisation and no signature check.
